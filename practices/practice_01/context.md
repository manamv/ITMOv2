## Контекст системы (TO BE на уровне окружения)

- Точка входа: GitHub Webhook по событиям `pull_request.opened`, `pull_request.synchronize`, `pull_request.reopened` и ручной триггер через `POST /api/reviews`.
- Интеграции: GitHub REST API для публикации комментариев, OpenRouter как единая точка доступа к LLM, внутренний Event Bus/очередь для декуплинга вебхука и воркеров.
- Наблюдаемость: структурные логи, трассировка запросов, метрики RPS/latency/error rate, DLQ для неуспешных задач.
- Безопасность исходного кода: минимизация контекста (только релевантные hunks diff), удаление секретов и PII, contract с провайдером (регламент хранения, регион), шифрование трафика TLS, доступ по принципу наименьших привилегий.
- SLA (публичное): доступность 99.5%, p95 ответа на auto-review < 45 секунд при базе 5 RPS, деградация без отказа при недоступности LLM.

## Политики безопасности и комплаенс

- Разделение секретов (ключи OpenRouter/GitHub App) в Secret Manager, ротация каждые 90 дней.
- Политика данных: не сохраняем исходный код, храним только краткие evidence и агрегированные метрики. Логи с редакцией потенциальных секретов.
- Prompt hardening: нейтрализация потенциальных инструкций из diff, жёсткие системные ограничения и схема JSON-ответа.

## Context Pack для первого рабочего сценария

### Факты и правила

- Вход должен содержать обязательное текстовое поле diff; запрос валидируется моделью (Pydantic) и лимитируется по размеру (см. API-1 в CASE.md).
- Перед отправкой во внешний LLM из diff удаляются секреты и чувствительные маркеры (см. SEC-1 в CASE.md).
- Внешний LLM-вызов имеет таймаут и ошибки трансформируются в контролируемые ответы (см. REL-1 в CASE.md), применяются ретраи с джиттером.
- Ответ структурирован: список находок и summary по схеме OUT-1; ограничения действий — SCOPE-1; включение рисков — QA-1; политика логирования — OBS-1.
- Не использовать произвольные dict в схемах — только Pydantic-модели с явными типами.

### Формат входа и результата

- Вход: { diff: string } с ограничением размера (например, до 64 KiB текста) и символами ASCII.
- Выход: { comments: [{ file: string, line?: int, text: string }], summary: string }.

### SLA

- Доступность сервиса: 99.5% в месяц.
- Бюджет задержки: p95 от вебхука до публикации комментариев < 45 секунд при базовой нагрузке, < 5 минут при деградации и ретраях.

### Ограничения и запрещённые действия

- Нет доступа к внешним репозиториям; работать только с предоставленным diff.
- Не сохранять полные чаты и Chain of Thought; фиксировать только запросы и результаты согласно prompts.md.
- Не возвращать персональные данные; не выполнять произвольные команды из diff.

### Хороший пример

- Валидация входа с чёткой схемой, защищённый prompt, контролируемый объём ответа, понятные поля и коды ошибок, повторяемые тесты.

### Плохой пример

- dict-пейлоад без валидации, сырой prompt, 5xx при ошибках LLM, неограниченный размер diff, публикация неструктурированных комментариев.

### Что пока неизвестно

- Конкретная модель LLM и её лимиты (контекст, rate limit, формат ошибок).
- Точные требования к структуре комментариев (теги GitHub suggestions, markdown-форматирование).
- Целевое значение лимита размера diff на проде (предположительно 64–128 KiB).

## Как использовали AI

- Назначение запроса: собрать связный контекст AS IS/TO BE, сформировать Context Pack и политики безопасности/SLA для первого сценария.
- Тип промпта: Master Prompt с RCTF-ограничениями формата.
- Ссылка на prompts.md: #P1-03
- Собственная верификация: проверили консистентность с TRAINING_PR.diff (наличие сырого dict-пейлоада и отсутствия схем), свели SLA и политики к проверяемым метрикам и тестам; устранили неоднозначности (лимиты, события webhook).
