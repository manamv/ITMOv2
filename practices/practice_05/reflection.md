Разработка велась строго по методологии **SDD (Spec-Driven Development)**: генерация кода началась **только после** взаимного согласования и утверждения единого контракта.

   * Рассчитывала переносить товары в корзину множественными HTTP-запросами в цикле.

   * Не предусматривала пакетной операции переноса в корзину.

## 3. Протокол согласования общего контракта (Negotiation Log)

Совместное обсуждение выявило 5 критических противоречий. В документе [`specs/contract.md`](file:///D:/3sem/vibecoding/ITMOv2/practices/practice_05/specs/contract.md) зафиксированы достигнутые компромиссы:

| # | Предмет расхождения | Позиция UI (Draft 1) | Позиция Logic (Draft 2) | Итоговое решение контракта | Обоснование |
|---|---------------------|----------------------|-------------------------|----------------------------|-------------|
| **1** | **Формат именования полей** | `camelCase` (`productId`) | `snake_case` (`product_id`) | **`snake_case`** | Единый стиль со всем существующим API VkusMart (`product_id`, `total_price`, `added_at`). |
| **2** | **Архитектура эндпоинтов** | `POST`, `DELETE /:id` | `/api/favorites/add`, `/api/favorites/remove` | **RESTful + Fallback** | Основные методы: `GET /api/favorites`, `POST /api/favorites`, `DELETE /api/favorites`, плюс `POST /api/favorites/remove` для совместимости. |
| **3** | **Обогащение данных (Enrichment)** | Только ID | Только ID и timestamp | **Обогащенный DTO (Enriched)** | Бэкенд возвращает полные данные (`Product.to_dict()`) + агрегаты (`total_price`, `total_calories`, `total_count`). Исключает рассинхронизацию цен и нагрузку на клиент. |
| **4** | **Идемпотентность добавления** | Игнорировать ошибки | Ошибка `400 Bad Request` при дубле | **Идемпотентный POST (200 OK)** | При повторном клике сервер возвращает статус `200 OK` с флагом `already_exists: true`. Это защищает UI от сбоев при быстрых двойных кликах пользователя. |
| **5** | **Перенос в корзину** | Цикл из N запросов | Не планировался | **Атомарный эндпоинт `POST /api/favorites/move-to-cart`** | За одну транзакцию сервер переносит все товары в корзину и очищает избранное, предотвращая race conditions и сетевой спам. |

## 4. Сравнение SDD-фреймворков: Spec-Kit vs OpenSpec

В качестве альтернативного SDD-фреймворка был выбран **Spec-Kit** (Specification-Driven Development Kit). Ниже представлен сравнительный анализ:

| Критерий | OpenSpec (из семинара) | Spec-Kit (выбранный в ДЗ) |
|---|---|---|
| **Основной фокус** | Пошаговый пайплайн изменений в brownfield (`explore` → `propose` → `apply` → `archive`). | Контрактное проектирование многокомпонентных систем и согласование спецификаций между командами. |
| **Модель управления изменениями** | Дельта-спецификации (`changes/<change-id>/proposal.md`, `specs/`). Изменение либо накатывается, либо отклоняется. | Матрица спецификаций компонентов (`ui-spec`, `logic-spec`) с арбитражем через общий контракт (`contract.md`). |
| **Взаимодействие команд** | Монолитный поток: один агент или разработчик ведет задачу от начала до архивации. | Распределенный поток: параллельные спеки команд (Frontend/Backend) с отдельной фазой Negotiation (согласование). |
| **CLI и автоматизация** | Детерминированный CLI (`openspec validate`, `openspec show`, `openspec instructions`). | Конфигурация через манифест (`spec-kit.config.yaml`), строгие схемы контрактов и валидаторы соответствия API. |
| **Применимость** | Идеален для быстрых локальных правок внутри одного репозитория одним агентом. | Идеален для межкомандного взаимодействия, микросервисов, проектирования сложных API и сквозных фич. |
| **Эргономика для LLM/Агентов** | Жестко заданные prompt-инструкции для каждого этапа CLI. | Явные контекстные границы: агент UI не видит лишних деталей БД, агент Logic не перегружен CSS/DOM. |

### Вывод по выбору фреймворка:
OpenSpec отлично автоматизирует рутину сопровождения кода в небольших задачах, но в сценарии «Две команды — одна фича» **Spec-Kit** проявил себя значительно мощнее. Он заставил выявить расхождения типов и протоколов **до** написания первой строчки кода, что полностью предотвратило переписывание логики на этапе интеграции.

## 6. Рефлексия: Чему научились и ключевые выводы

1. **Главная ценность согласования до кода:**
   Если бы мы начали кодить сразу по драфту UI, мы бы потратили часы на отладку: UI отправлял бы `productId` вместо `product_id`, падал бы на ошибке 400 при повторном клике по сердечку и слал бы десятки разрозненных запросов при переносе в корзину. Фаза контрактования заняла 15 минут, но сэкономила всё время на интеграции.
2. **Идемпотентность в пользовательских интерфейсах:**
   Решение сделать `POST /api/favorites` идемпотентным — фундаментальный паттерн в веб-разработке. Быстрые клики (double click) или сетевые повторы часто приводят к ошибкам 400/409, если API спроектирован без учета реального поведения пользователя.
3. **Обогащение данных (Enrichment) vs Разгрузка сети:**
   Компромисс между передачей только ID и передачей полного объекта товара был решен в пользу обогащенного DTO. В brownfield-проектах это снимает проблему гонки состояний и гарантирует, что пользователь видит актуальные цены в избранном без дополнительных запросов к каталогу.
